push前に以下を確認する。

- git status(未コミット・未追跡ファイルの有無)
- 現在のbranchとpush先
  - コードの変更: 作業ブランチにpushする(mainに直接pushしない)
  - 文書だけの変更: mainに直接pushしてよい
  - 公式サイト(latefolar-web)のリポジトリ: 取り込み方が決まるまでは、どちらにするかをユーザーに確認する
- git diff / git diff --cached(意図しない変更が含まれていないか)
- push対象のコミット一覧(push先のリモートブランチとの差分。作業ブランチの場合は origin/main との差分も)
- 意図的な未コミット変更(例: ローカル開発用のLAN-IP設定等)がpush対象に含まれていないか
- push対象のコミットのauthorとcommitterが、どちらもnoreplyのアドレスか(noreplyでない場合は、そのアドレスをチャットにも報告にも書かない)
- force pushが必要な状態(リモートの方が進んでいる、履歴を書き換えた等)になっていないか。なっている場合はpushせずに報告する

## 注意

- この確認自体ではpushしない。確認結果を報告し、ユーザーからの明示的な指示を待ってからpushする
- 問題が見つかった場合は、憶測で修正せず、まず状況を報告する
- PR・CI・承認・Rebase and merge・取り込み後の確認の流れは、共通の開発の決まり(D:\salary-countup-app\docs\dev-rules.md)の 6. と 8. に従う。この手順と決まりが食い違う場合は決まりを優先し、食い違いを報告する

## 複数リポジトリ(バックエンド/iOS/Android)を跨ぐ変更の場合

- 依存関係のある変更(例: APIのwire format変更)は、各リポジトリでPRを用意してCIを通しておき、バックエンド→iOS→Androidの順に続けて取り込み(Rebase and merge)、片方だけ新仕様になっている時間を最小化する
- 前のリポジトリの取り込みと、mainのCI成功を確認してから、次のリポジトリへ進む(決まりの 8.)
